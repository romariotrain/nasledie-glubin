# Что улучшать дальше и какими инструментами

Дата оценки: 23.10.2026. Это предложения, не уже выполненные функции и не
разрешение агенту автоматически установить все пакеты. Критерий инструмента:
какую повторяющуюся потерю времени он убирает в нашем конкретном процессе.

## Сначала сохранить полученную базу

**P0 — исходники и восстановление.** Git существует, Git LFS установлен, однако
в `unity/`, `art/`, `tools/` нет отслеживаемых файлов. Приоритет — не новый генератор,
а осмысленный первый коммит игры и резервная копия. Сохранять Assets вместе с
`.meta`, Packages/manifest и lock, ProjectSettings, текущий .blend, карты, FBX/GLB,
референсы, скрипты и отчёты. Большие бинарные источники — кандидаты для Git LFS;
точный набор выбрать после инвентаризации. Library, Temp, локальные веса и кеши
не нужны в Git. Старые версии/превью можно держать в архивном хранилище с manifest.

Вместе с исходниками сохранять происхождение артов, текстур, модели и условия
используемых инструментов/весов. В `tools/hunyuan/README.md` записаны upstream
revision и Tencent Hunyuan3D 2.0 Community License; это отдельная запись, а не
основание автоматически пометить весь набор ассетов MIT. Условия выпуска в этом
разборе юридически не оценивались.

Второй критерий P0: копия проекта открывается на другом пути и собирается без
ссылок на прежнюю папку Desktop. Восстановление Unity и восстановление генератора
Hunyuan — две отдельные задачи. Веса не требуются для готовой сцены. Не считать
синхронизацию OneDrive доказательством проверенного восстановления.

Коммит/удаление старых исходников/публикация remote этим разбором не выполнялись.

## Следующая игровая проверка

**P1 — один настоящий противник и двухминутный бой.** Один враг умеет заметно
готовить удар, атаковать, получать попадание, умирать; игрок получает урон и может
перезапустить бой. Сначала один тип, не большой каталог противников и классов.
Критерий: дистанция атаки, рывок, выпад и третий удар отличаются по назначению,
а правила отмены понятны без объяснения автора. Затем 5–10 врагов, потом 10–30.

Параллельно записывать по короткой видеопробе: бег прямо/повороты/старт/стоп,
комбо, уклонение, выпад. Пользовательская оценка «стало лучше» и технический PASS
сохраняются раздельно. Это полезнее следующей безадресной переработки модели.

**P1 — бюджет кадра.** Выбрать целевой компьютер/разрешение/число врагов и измерить
CPU, GPU, аллокации, материалы, draw calls и тени в Development Build. Если цель
60 fps, общий ориентир — 16,7 ms/кадр, но ещё нужно распределить бюджет по системам.
Имеющихся проверок недостаточно, чтобы объявить 12k треугольников причиной лагов
или доказать запас производительности в толпе.

## Художественный и технический долг

| Приоритет | Правка | Как принять результат |
|---|---|---|
| P1 | Короткая визуальная спецификация: камера, размер героя на экране, 2–3 образца света, ткани, камня и металла | Следующий ассет попадает в ту же сцену без новой дискуссии о стиле с нуля |
| P2 | Ручная/полуавтоматическая шлифовка run, старт/стоп и поворотов | Нет заметного скольжения, резкого перехода рук или неуместного подпрыгивания на видео |
| P2 | Плечи/кисти/пальто на смешивании клипов | Несколько фиксированных переходов и крупные кадры; не обещать отсутствие всех пересечений |
| P2 | Проверить боковые UV, швы и освещение в basecolor | Модель предсказуемо выглядит под несколькими направлениями света |
| P2 | Единый config для asset version, scene revision, prefab, tuning, checks | Новая версия не требует правки нескольких Python/C#/PowerShell-файлов |
| P2 | Журнал автоматических прогонов и единая команда приёмки | Ошибочный экспорт/пустой кадр/ошибка runtime останавливают приёмку |
| P3 | Модульная экипировка | Только когда её требует геймплей; текущий основной меш не считать готовым набором одежды |
| P3 | LOD/упрощённые карты/пулы эффектов | После измерения конкретного узкого места, с до/после и визуальным сравнением |

Автоматический `Setup` сцены сейчас может затереть ручное оформление, а MakeTuning
заново выставляет часть значений. Перед масштабированием вынести ручной уровень
из пересоздаваемого генератором содержимого, закрепить prefab/материалы/данные.

## Навыки и связь с редактором

В текущем Codex-сеансе уже доступны Unity skills. Для работы сейчас полезны
`unity-cli`, `ui-imgui` для существующего HUD, `physics-3d-collision` при реальных
проблемах попаданий и `initialize-ai-navigation` при появлении врага.
`game-asset-production` и `game-asset-vendoring` сохраняют разделение производства
и импорта. Набор навыков не означает, что все они были применены к этому прототипу.

На машине обнаружен **Unity CLI 1.0.0-beta.13**. `unity pipeline list` сообщает,
что у SwordsmanCombatTest нет Pipeline package и доступного сервера. `unity status`
не смог полностью проверить процессы из песочницы; это не свидетельство закрытого
Editor. Проверка доступного обновления CLI была заблокирована доступом к локальному
proxy; актуальность версии не подтверждена. Настройки proxy не менялись.

Самый предметный следующий эксперимент — подключить локальный Pipeline и проверить
цикл: обнаружить именно этот Editor → прочитать сцену → сделать маленькую обратимую
правку → дождаться компиляции → убедиться, что Play действительно идёт → снять
кадр и прочитать Console. Это может уменьшить потребность в служебной копии проекта.
Возможность управления Editor через CLI/Pipeline описана в
[официальном навыке Unity](https://github.com/Unity-Technologies/skills/blob/main/skills/unity-cli/SKILL.md).
Подключение в этом разборе не выполнялось.

Для Claude Code есть [официальный Unity plugin](https://github.com/Unity-Technologies/unity-agent-plugin)
и [набор Unity skills](https://github.com/Unity-Technologies/skills). Это полезнее
случайного набора похожих MCP-серверов. Локальная документация установленного CLI
описывает `unity setup claude --dry-run`, `unity mcp configure --list` и настройку
по клиенту; запуск установки меняет конфигурацию клиента, поэтому это отдельная
осознанная задача. Claude в обычном веб-чате, без доступа к файлам и инструментам,
сможет прочитать handoff, но не управлять Unity только от наличия текста skill.

Свой будущий навык стоит сделать узким: «итерация персонажа в существующем Unity
проекте», а не «создай любую игру». Основа уже записана в [AGENT_WORKFLOW.md](AGENT_WORKFLOW.md).
Его пока не устанавливали как автоматически обнаруживаемый skill. Сначала проверить
протокол на второй небольшой задаче, затем упаковать для выбранного агента.

## Какие GitHub-проекты имеют смысл

| Источник | Конкретная польза | Когда брать |
|---|---|---|
| [Unity-Technologies/skills](https://github.com/Unity-Technologies/skills) | Официальные инструкции агентам; доступны для Claude Code и других клиентов | Сейчас, через штатный plugin; не клонировать содержимое в Assets |
| [Tencent-Hunyuan/Hunyuan3D-2](https://github.com/Tencent-Hunyuan/Hunyuan3D-2) | Наш существующий backend формы | Сохранить проверенный revision, параметры и ссылки на веса; не обновлять ради самого обновления |
| [game-ci/unity-builder](https://github.com/game-ci/unity-builder) и [unity-test-runner](https://github.com/game-ci/unity-test-runner) | Сборки и тесты в CI | После Git-базы; потребуются настройка Unity activation и адаптация тестов |
| [Project Auditor](https://github.com/Unity-Technologies/ProjectAuditor) | Анализ проекта | Старый GitHub-репозиторий сам помечен устаревшим и неподдерживаемым; смотреть актуальный Unity package, не клонировать master |

Наши 24 проверки — собственный GPU runtime smoke-run Windows executable, а не
уже готовые NUnit PlayMode-тесты. Подключение GameCI test-runner само по себе их
не запустит. Нужен перенос/адаптер и подходящая среда для рендера. Для CI не
передавать логины/ключи агенту в переписке; настройки хранятся штатно в окружении.
См. [документацию GameCI](https://game.ci/docs/github/getting-started/).

Для производительных сценариев существует
[Performance testing API Unity](https://docs.unity.com/en-us/engine/6000.0/manual/packages-list/packages-all/pack-safe/com-unity-test-framework-performance),
но сначала нужен воспроизводимый сценарий нагрузки, затем выбор совместимой версии.

## Что сейчас не даёт ожидаемого выигрыша

Смена движка/рендер-пайплайна, ECS, новый риггер, ещё один генератор формы и сразу
несколько MCP-серверов добавят неизвестные до измеримого результата. Платные
motion-capture/retopology/texture инструменты можно сравнить позже на одном
фиксированном кейсе: время исправления, качество на игровой камере, цена, объём
ручной работы и воспроизводимость. Сейчас главные ускорители — сохранённая база,
связь с Editor, конфигурируемая сборка и короткая игровая проверка.
