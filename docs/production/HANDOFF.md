## Первый безопасный шаг

Прочитать `AGENTS.md`, этот файл, README сцены и README текущего персонажа.
Затем из корня в PowerShell:

```powershell
$py = '.\work\hunyuan2mini\.venv\Scripts\python.exe'
& $py tools/character_pipeline/audit_baseline.py
git status --short
```

Аудит читает сохранённые отчёты и сравнивает хеши. Это не новый игровой прогон.
При расхождениях сначала понять пользовательские изменения; не откатывать их
автоматически и не «исправлять» receipt, чтобы скрыть отличие.

Существующая история Git пока не включает игру/ассеты/инструменты. Если передан
только нынешний Git clone, этих файлов там может не быть. Нужна фактическая копия
проекта либо предварительно зафиксированная исходная база.

## Запуск и проверка

Открыть папку Unity-проекта в Hub; затем сцену DungeonCombatTest и Play.
Либо запустить .exe из `work/unity-dungeon-test/Build`. Для переноса игры нужны
все соседние DLL и Data-папки, не один executable.

WASD — бег, ЛКМ — комбо, Space/Shift — рывок, E/ПКМ — выпад, колесо — масштаб,
F1 — панель, V — области попаданий, H — тест урона, R — сброс.

Новая сборка и проверки:

```powershell
./tools/unity/Build-Dungeon.ps1 -Test -Revision v004
```

`v004` здесь пример **новой** папки отчёта. Builder всё ещё перезаписывает рабочую
сцену, текущую Build-папку и часть именованных материалов. Перед запуском сохранить
нужную старую сборку/сцену; версия отчёта сама этого не делает. Игра из Build должна
быть закрыта. Открытый пользовательский Editor не закрывать: скрипт собирает
служебную копию `work/UnityDungeonPreview_v001`, затем переносит новую сцену,
её ассеты, prefab и tuning с их .meta. Не открывать эту копию как основной проект.

Скрипт генерации сцены заново создаёт её содержание: перед его применением к
вручную оформленной сцене сохранить отдельный вариант. Изменения скорости в
MakeTuning тоже могут перезаписать параметры текущего профиля.

Проверять `work/unity-dungeon-test/build-result.json`, `runtime.log` и новый
`Validation/dungeon_<revision>/runtime-test-report.json`. Сейчас ожидаются 24 checks.
Для изменения их состава обновить валидатор: в нём пока есть привязки к версиям.

`seal_dungeon_validation.py` дополнительно требует просмотренный непустой кадр
обычного окна `unity_playtest.png`. Сама успешная сборка или вход в Play этого
не заменяют. Захват скрытого окна может быть чёрным; RenderTexture не захватывает
OnGUI так же, как обычный оконный screenshot.

## Изменение ассета

Не выполнять генерацию заново ради небольшого изменения движения. Для новой
версии брать текущий .blend, сохранять новую папку, фиксировать scope в receipt,
сохранять непричастные клипы и проверять только действительно изменившиеся превью.
Примеры: `lower_free_arm_v009.py`, `lengthen_run_v010.py`. Не запускать их повторно
как универсальные команды: в них указаны конкретные версии/риг.

Последовательность: spec/новый job → правка → контакты/поза/цикл → экспорт →
повторный импорт и check-export → превью → package manifest → admission → Unity.
Точные инструменты и границы: `tools/character_pipeline/README.md`.

Новая генерация требует локального upstream checkout, модели, среды и зависимостей
из `tools/hunyuan/README.md`. Полная установка на чистой машине ещё не проверена.
Для открытия готового Unity-проекта веса Hunyuan и Python не нужны.

## Проверки и запреты на необоснованные выводы

24 runtime-проверки покрывают направление, клипы, комбо/урон, перемещение,
неуязвимость, отмены и стены. Нет AI-врага, очереди толпы или профилирования FPS.
Одежда проверяется выборкой нижнего кафтана против ног, не по всем поверхностям
и смешанным позам. Хват фиксированный, пальцы отдельно не анимируются.

Не путать технический PASS с художественным одобрением. Не переписывать проект
на другой движок, не подменять геройскую модель, не менять root-motion policy,
не ставить пакеты/платные сервисы или не публиковать проект как часть иной задачи.
Сначала выполнять конкретную задачу пользователя на сохранённой базе.
