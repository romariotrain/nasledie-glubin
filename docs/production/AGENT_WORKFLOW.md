# Переносимый протокол итерации

Это обычная инструкция проекта, применимая в Codex, Claude Code и другом агенте
с файловыми инструментами. Это не установленный автоматически вызываемый skill.

## Когда использовать

Изменение уже существующего персонажа, анимации, материалов или тестовой сцены.
Для нового персонажа сначала адаптировать spec и анатомию: скрипт мечника не
объявлять универсальным генератором рига или ретопологии.

## Порядок работы

1. **Прочитать актуальную базу.** HANDOFF, AGENTS, соответствующий README и spec.
   Проверить сохранённые хеши и git status; найти пользовательские изменения.
2. **Определить, какое свойство проверяем.** Форма, цвет, свет, каденс, тайминг,
   контроль направления — разные переменные. Записать одно предложение о результате.
3. **Подготовить честное сравнение.** Для силуэта — одинаковая однотонная подача.
   Для материала — та же модель/поза/камера. Для движения — целый цикл в масштабе игры.
4. **Менять минимальный необходимый слой.** Проблема кисти не требует новой
   Hunyuan-генерации; стилистическая проба не требует смены рендера или движка.
5. **Сохранить новую версию и scope.** Source hash, параметры, источник изображений,
   изменённые клипы, неизменённые части и ограничения. Не стирать предыдущую базу.
6. **Проверить только то, что действительно затронуто.** После правки анимации:
   конечности, корень, сокет, цикл, одежда; после экспорта — повторный импорт;
   после Unity-правки — компиляция, нужный runtime-сценарий, фактический рендер.
   Не повторять тяжёлые прогоны без изменения или новой причины.
7. **Согласовать скорость.** Для in-place бега reference speed, период, траектория
   опорной стопы и скорость контроллера должны описывать одно движение. Правило
   `playbackRate = actualSpeed / referenceSpeed` само по себе не исправляет плохой шаг.
8. **Проверить сам путь импорта.** Копировать только проверенные байты вместе с
   .meta/receipt. .blend-кадр не считать доказательством корректного FBX в Unity.
9. **Посмотреть в движке.** Снимать реальную камеру, проверять, что игра идёт и
   Console не содержит ошибок. В скрытом окне не полагаться на обычный screenshot.
10. **Записать урок.** Жалоба → причина → изменение → доказательство → оставшееся
    ограничение. Исправление поведения с риском регрессии закрепить сценарием проверки.

## Стоп и восстановление

При несовпадении хешей сначала исследовать отличие. При ошибке сборки не показывать
старый screenshot как новый. При художественном сомнении дать дешёвые варианты,
не объявлять эксперимент финальной моделью. При открытом пользовательском Editor
не закрывать несохранённую сцену для удобства автоматизации. При отсутствии нового
инструмента продолжать рабочим проверенным способом, явно описав ограничение.

## Короткая запись результата

```text
Версия / исходник / hash:
Запрос пользователя и критерий:
Изменено:
Проверено, с путями к отчётам:
Посмотрено в движке:
Ограничения:
Следующий небольшой шаг:
```

Техническая приёмка, художественная оценка и производительность — три отдельные
строки. Слово «готово» всегда относится к указанной задаче и области проверки.
